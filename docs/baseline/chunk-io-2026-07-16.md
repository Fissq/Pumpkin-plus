## Задача 1: flat-мир доходит до Full через планировщик

После фикса `6fcc5697` (livelock Structure*-стадий) flat-мир с тикетом 43
проходит планировщик до Full за **0.53 с** (debug-сборка, один чанк).
Порядок стадий чанка (0,0), снят временной трассировкой `Cache::advance`:
Biomes → StructureStart → StructureReferences → Noise → Surface → Carvers →
Features → Lighting → Spawn → Full. Зависание, наблюдавшееся до фикса,
целиком объяснялось пустыми flat-ветками Structure*; отдельного PR не
требуется. Временный тест и трассировка удалены.

## Сценарии бенча (Anvil, сид 42)

- **hot** — 64 noise-чанка (8×8, регион r.0.0), сериализатор региона
  удерживается в кэше watcher'ами. Важно: текущий код при watched-регионе
  **вообще не пишет на диск** (flush отложен) — сценарий изолирует чистую
  стоимость сериализации+LZ4 и является нижней границей для PR1.
- **cold** — текущее продовое поведение: каждый save перечитывает весь
  регион, переписывает его и эвиктит сериализатор. Перед замером регион
  предзаполнен (steady state).
- **fill** — «прегенератор»: пустой регион, 16 порций по 64 flat-чанка
  (до полных 1024), save после каждой порции; счётчики — суммарно за всё
  наполнение.

Полезный объём (payload):
- noise64: NBT (несжатый) 4 767 091 Б; файл региона (сжатый, с паддингом
  секторов и заголовком) **827 392 Б**.
- flat1024: NBT 55 609 344 Б; файл региона **4 202 496 Б**.

## Результаты (медианы двух прогонов; байты идентичны в обоих)

| Сценарий | write_in_place | Время (run1 / run2) | Байт записано | Байт прочитано | Усиление записи* |
|---|---|---|---|---|---|
| hot (64 чанка) | false | 15.20 / 15.51 мс | 0 | 0 | 0 (flush отложен) |
| hot (64 чанка) | true | 15.88 / 16.47 мс | 0 | 0 | 0 (flush отложен) |
| cold (64 чанка) | false | 16.50 / 16.94 мс | 827 392 | 827 392 | ×1.00 |
| cold (64 чанка) | true | 16.94 / 17.55 мс | 827 392 | 827 392 | ×1.00 |
| fill (1024 чанка) | false | 234.5 / 235.5 мс | 35 782 656 | 31 580 160 | **×8.51** |
| fill (1024 чанка) | true | 204.3 / 205.6 мс | 4 325 376 | 31 580 160 | **×1.03** |

\* усиление записи = байт записано / размер итогового файла региона
(для cold — за одну итерацию save; для fill — за всё наполнение).
Разброс медиан между прогонами 0.4–3.7% (< 10%, стабильно).

## Выводы

1. **Cold vs hot:** по времени на NVMe холодный путь дороже лишь на
   ~1.3–1.4 мс (+9%) — page cache прячет диск. Но по I/O разница
   принципиальная: 827 КБ чтения + 827 КБ записи на каждый save региона
   против нуля. Выигрыш PR1 (LRU-кэш сериализаторов) на dev-машине надо
   принимать по байтам, а не по мс; на HDD/btrfs (FX-4300) байты и есть
   время.
2. **write_in_place false vs true (cold, все 64 чанка dirty):** байты
   идентичны — когда грязен весь регион, Parts-запись эквивалентна полной;
   по времени wip даже чуть хуже (+0.6 мс, сики вместо линейной записи
   tmp-файла). Выигрыш wip проявляется только при частичной грязности —
   см. fill. Для решения о дефолте нужен сценарий «1 грязный чанк из 64»
   (TODO PR1).
3. **Fill (прегенератор):** усиление записи при наполнении региона
   подтверждено и равно теоретическому **N ≈ (16+1)/2 = 8.5** для
   write_all (каждая порция переписывает весь накопленный файл);
   write_in_place снимает его до ×1.03. Однако **чтение** остаётся
   ×7.51 (31.6 МБ на 4.2 МБ регион) в обоих режимах — эвикция после
   каждого save заставляет перечитывать растущий регион перед следующей
   порцией. Полный потенциал wip+LRU на прегене: ~67 МБ I/O → ~4.3 МБ
   (≈×15 меньше) на регион.
4. **Стоимость сериализации** (hot): ~15.5 мс на 64 чанка ≈ 0.24 мс/чанк
   (NBT + LZ4, один поток) — при прегене 460 чанков/с это ~110 мс/с CPU,
   т.е. ~11% одного ядра только на сериализацию; в текущем коде она
   выполняется в единственной io_write-задаче (аргумент за распараллеливание
   в PR2+).

## Наблюдение для feat/bitexact-tests

Несжатый NBT-объём 64 noise-чанков различается между двумя запусками
процесса на 578 Б (4 767 091 против 4 766 513) при идентичных сжатых
файлах регионов по размеру и идентичных счётчиках I/O. Внутри одного
процесса значение стабильно. Похоже на межпроцессную недетерминированность
порядка/состава какой-то NBT-структуры (кандидаты: std HashMap с ASLR-зависимым
RandomState в пути фич/блок-энтити). Для бит-точности мира это красный
флажок — проверить дампами в ветке `feat/bitexact-tests`.
